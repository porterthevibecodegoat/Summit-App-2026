GUEST FLOW
1. The existing wellness form collects the same contacts, class choices and signed waiver. New booking behavior is disabled unless explicitly configured.
2. A stable request UUID plus a payload fingerprint makes retries reuse the original intake. The browser retains only that UUID/hash, not contacts, in sessionStorage. Changed input gets a new request ID. Cached older forms carrying their existing UUID remain accepted.
3. An immutable private intake preserves the original per-class IDs, timestamp, waiver and contact payload before seat assignment. One conditional ledger write assigns the complete class batch, queues full classes, and records an audit event. Simultaneous requests cannot overwrite seat counts. The existing three-form-submission policy counts intakes, not individual class rows.
4. Per-class workshop records are saved to the existing canonical/journaled source with stable IDs. A second conditional ledger write acknowledges the entire intake. Until this completes, all its classes are held from reminders. Staff recovery or the same guest retry completes a partial save without taking another place or changing the original waiver timestamp.
5. Success displays Registered or Waitlisted with a queue position. A private management link lets the guest view and cancel that intake's own classes. It is a signed capability in a URL fragment, expires 24 hours after the last selected activity ends, and contains no contact details. It never enters query strings or the raw submission inbox. Anyone with the link can use it; guests are told to keep it private. A new anonymous request cannot retrieve another intake's link.
6. Cancellation is a separate ledger transition; source submissions, waiver history and earlier audit events are retained. Repeated cancellation requests are safe. The next eligible waitlisted booking is promoted in the same conditional write. A STOP reply suppresses messaging and does not cancel the person's place.

DRAFT OPERATIONAL DEFAULTS FOR COMPLETE-PROCESS REVIEW
- New signups and guest/staff cancellations close when the activity starts. Retired activities remain in history and may be cancelled without promotion.
- A staff hold/decline/zero allocation or a removed/test source row blocks waitlist promotion. Existing registered places are not automatically released by an approval edit; use the new explicit cancellation action to release a place. STORAGE AND SAFETY
Server-only settings:
  WELLNESS_BOOKING_ENABLED: default unset/false.
  WELLNESS_BOOKING_MODE: explicit test or live.
  WELLNESS_MANAGEMENT_SECRET: separate 32+ character secret, provider settings only.
  INTEGRATION_SMS_SEND_APPROVED: MUST remain unset/false until complete approval.

Netlify live mode requires production context, a complete approved capacity policy, no test prefix, and an already initialized reviewed ledger. It cannot initialize an empty live ledger. The main web app writes wellness/ledger-v1.json through conditional ETags and immutable wellness-intakes/<uuid>.json plus journal copies in the canonical staff-portal store. The companion reminder service has read-only ledger access and no booking/outbox mutation capability.

Isolated test mode requires a nas-reminders-test-* prefix and an explicitly labelled test-only capacity JSON/file; it is rejected on the public Netlify production context. Local tests additionally require an explicitly named isolated directory. Canonical source, raw inbox, private intakes and ledger all stay within that test scope. Merely constructing a workflow does not create records. Test sample limits cannot pass the live policy gate. Local rehearsal secrets/guests are fictional and are not checked in.

The feed requires its own bearer secret. It returns sendApproval=pending, previewJobs, and reminderJobs=[] while the SMS approval flag is false/unset. Website code and companion functions contain no outbound SMS sender. Keep Make inactive; do not use Run once on any SMS flow before approval. A test pass, merge, deployment or review is not permission to send.
