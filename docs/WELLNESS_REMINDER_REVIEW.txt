REMINDER FEED
GET /api/integrations/agenda requires its own random server-side bearer secret of at least 32 characters. It reads only workshop, textPreference and programApproval records. Only category=wellness records with a canonical wellness ID qualify. It derives titles and UTC instants directly from lib/wellness-signups-2026.ts; no second class schedule is maintained. There are currently 30 choices. Other RSVP, dinner, site-visit and admission configuration cannot enter this API.

Ordinary wellness signups do not need an additional staff approval. If a matching programApproval exists, the newest exact source-record/class decision controls: hold, decline, zero approved quantity, and contact hold all suppress reminders. An approved record must be ready or sent in the existing contact queue. Tied holds beat approvals. Staff approval and confirmation code is unchanged. This conservative contact-hold interpretation should be reviewed with Porter/Cherrial before production.

The feed validates contact identity, separates event-only permission from broader updates consent, suppresses STOP by phone/email aliases, and holds numbers shared by different named guests. A new checkbox does not undo STOP. Only a later positive preference for the same phone can clear it. It keeps latest per-class selections across phone/email edits and does not revive older registrations behind cancellation/removal markers. Any required source failure returns 503 without partial recipients or contact details. All responses prohibit caching.

The planner produces one combined agenda at 7 PM on the previous Las Vegas evening and one reminder 60 minutes before each selected class/window. Job keys remain stable across retry, email edits and rescheduling. Drop-ins are described as windows. No room is invented. Make must revalidate the current complete job immediately before dispatch and own durable send reservations, provider outcomes and delivery reconciliation. Snapshot reads span multiple sources and are not a single transaction with ClickSend.

The booking domain supports atomic batches, idempotent request IDs, duplicate-attendee suppression, registered/waitlisted/cancelled states, FIFO promotion after cancellation, owner-key checks, conflict validation, immutable audit events, and strict stored-state validation. The whole transition uses one conditional ledger write; concurrent requests cannot overwrite each other's seat counts. Netlify adapter reads strongly, uses onlyIfNew for explicit isolated initialization and onlyIfMatch for an existing ETag; a conflict retries the complete operation.
